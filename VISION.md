# Vision

Hygguile is a component library for people who think a web page is a document and a server is the right place to finish it. You write pages as S-expressions, the components return SXML, and what leaves the process is complete, accessible HTML that works when JavaScript does not. This document is about what that position demands next — from the serialiser, from the test suite, and from the uneasy gap between "a component library" and "a framework".

## Where hygguile is today

The tree is large and specific: thirty modules under `src/hygguile/components/`, about fifteen thousand lines of Scheme, and a shape that is almost a catalogue rather than a library. `field.scm` alone is 2,195 lines and covers the shell around a control — label, help text, error slot, `aria-describedby` wiring — plus every native input, a `combobox`, a `multi-select`, an `otp-field` and the rules-to-summary end of validation, which turns a list of `(field . message)` pairs into the summary announced on load. `table.scm` is 1,039 lines of the whole `<table>` family with a scroll region, server-driven sorting and selectable, resizable, dense modes. `typography.scm` names its procedures after the elements they produce, which is the project's central convention and its best idea.

Underneath is Olive CSS as the utility layer, plus `hygguile-extras.css` for the things a utility class cannot express — the switch, the CSS-only modal and tabs, the tooltip, the frosted panel — plus `no-js.css` and a separate `fly-out.css`. Eighteen small scripts live under `resources/js/`, each with one job, and `maak embed` rewrites them into `src/hygguile/embed/` so a consumer needs no asset pipeline. The `tokens` module publishes the design decisions as CSS custom properties *and* reads the same values in Scheme, which is what lets a component be written against a decision rather than a literal.

Three decisions constrain everything below.

1. **Native HTML first.** A `table` is a `<table>` with a `<caption>` and `<th scope>`; an `input` is an `<input>` with a `<label for>` bound to it; a modal is `:target`, a dropdown is `<details>`, a popover is the Popover API. A component that cannot be expressed this way is either re-designed or given a script that only enhances.
2. **No hydration, no second source of truth.** A page is a pure function of its request. There is nothing on the client to disagree with the server, no client router, and no bundle to download before the first pixel.
3. **The showcase is the storybook.** `showcase.scm` and the per-shelf modules beside it are the kitchen sink and the visual contract; `maak build` renders them and then runs the contrast gate over every text pair in every theme, exiting non-zero when one is below WCAG AA.

Two smaller disciplines are worth naming because they are unusual and because this document leans on both. The version lives in exactly one place — `hygguile-version` in `version.scm`, deliberately in a non-declarative module so that Guile cannot inline it into a consumer's compiled file and leave a page printing a version its source disagrees with — and `maak sync-version` rewrites the copies, commits and tags. And the packaging recipes for Debian, openSUSE and Arch live in the repository beside the sources, pinned to the same tag, so a recipe cannot drift from the code it builds even though none of the three archives ships it yet.

The roughly thirty specs under `test/veritas/unit/` follow the same pattern as the modules: one per component family, asserting on the SXML a component returns — the attributes it sets, the `aria-*` it wires, the text it escapes — plus a spec for the serialiser and one for the abstraction helpers the components are written with. It is a suite that tests the layer hygguile actually controls, which is the correct instinct and also the reason statements 1 and 3 below are about what it cannot see.

What the tree is honest about: it is a young framework whose minor releases may still rename a component or change the markup it emits, and it says so. Two `FIXME` comments sit in `sxml.scm` on name validation, which is the one place in the pipeline where a mistake escapes as broken markup rather than an exception. The accessibility suite checks *shape* — labels present, `aria-*` wired, roles right — rather than what a browser actually builds from it.

None of that is unusual for a young framework, and all of it is fixable. What is unusual is that the project already publishes the rule it wants to be held to, in a table it calls the contract: every row names the components that implement it. A contract nobody executes is a design document; making it executable is the work.

The gap between those two sentences is the whole of this document. Hygguile's components encode an enormous amount of accessibility knowledge, and the suite verifies that the knowledge was written down; nothing verifies that a browser agrees with it. The same asymmetry appears in two more places: a key argument typed wrongly is silently dropped rather than rejected, and the eighteen enhancement scripts are embedded into Scheme by a task nothing forces you to run. Correctness that depends on the author remembering is correctness that the next contributor will break without noticing.

The development loop is the project's strongest habit and worth protecting. `maak validate` formats, compiles and tests; `maak build` renders the showcase and the minimal example and then runs the contrast gate; `maak docs` regenerates the reference from the docstrings, which are written in Texinfo with `@table`, `@item` and `@example` because the reference is generated rather than hand-written; `maak dev` watches the tree and re-runs all three. A change is one command away from being checked, and the checking is the same run a consumer would do.

## The vision

1. **A component call cannot be wrong silently.** `(input #:lable "Email")` currently renders an input with no label, because a `#:key` argument Guile does not recognise is simply not bound. In a few years every component declares the key arguments it accepts, and an unknown one, a missing required one, or a combination that cannot work raises at the call with a message naming the component and the argument. This is the single largest quality gap in the project, and the one a beginner hits first.
2. **Escaping and name validity are proved, not assumed.** `sxml.scm` is hygguile's own serialiser rather than Guile's, because `text/html` reads a self-closing `<div />` as an open tag that swallows the rest of the document — a real bug the standard serialiser has. The remaining `FIXME`s are the rest of the same argument: an invalid element or attribute name must be an error at serialisation, and a property-based test over generated trees should show that no text or attribute value can reach the output unescaped.
3. **Accessibility is measured on the rendered page, not asserted on the SXML.** The contrast gate already does this for colour, by driving a real Chromium over the built showcase. The same harness should check what the shape tests can only approximate: that every form control has an accessible name in the accessibility tree, that focus order follows reading order, that no component removes a focus ring, and that the disclosure-based components expose their state.
4. **A reference application binds hygguile to a server, and it is part of the project.** Everything a server-rendered UI needs beyond components — form decoding, the round trip that puts `validation-errors` back into a page, redirect-after-post, CSRF, a 404 that uses `error-state` — is currently re-invented per consumer. LucidPlan does it by hand on Artanis. In a few years there is a thin, documented contract, with Artanis as the reference implementation and the option of another server behind it.
5. **It ships in the distributions it already has recipes for.** `packaging/debian`, `packaging/opensuse` and `packaging/arch` exist and are pinned to the same release tag as the sources, and none of the three archives carries the package yet. A library that a distribution can install is a library whose bugs get reported by people who are not already Scheme programmers.

Statements 1 and 2 are about not lying; 3 is about not guessing; 4 and 5 are about reach. The ordering is deliberate. A framework that silently drops an argument, or emits markup nobody checked, will lose a contributor at the first bug they cannot explain — and reach is worth nothing without them.

## Features that are in scope and not built yet

Each of these is a seam the code has already cut.

- **Declared key arguments.** Every component takes `#:key` arguments in a lambda, and `showcase.scm` plus the docstrings are the only record of which ones exist. *The hard part* is that Guile has no static types and no declarative arglists, so the declaration has to be invented — a macro that generates the lambda *and* a queryable record — and then retrofitted to thirty modules without changing a single call site.
- **Name and text validation in the serialiser.** Two `FIXME`s in `sxml.scm`. *The hard part* is doing it without a measurable cost on the hot path, since `sxml->xml` runs once per element of every page.
- **A DOM-level accessibility audit.** `maak contrast` already launches a browser and reads computed colour. *The hard part* is that the assertions that matter are structural and stateful — an accessible name is a computation over a subtree, and a focus trap is a behaviour — so the harness needs a real accessibility-tree reader rather than a query over markup.
- **A golden-markup corpus.** The unit suite asserts on the SXML each component returns, which is the right level for behaviour but says nothing about the markup a refactor changes. *The hard part* is that a golden file regenerated whenever it fails is worse than no golden file, so the corpus needs a review discipline the project does not yet have.
- **Token discipline as a test.** Tokens are published and readable from Scheme, and many components still reach for a utility literal. *The hard part* is that the exception is legitimate — a one-off clamp or a ratio is not a design decision — so the rule needs a way to say "this literal is deliberate" that is not a comment.
- **`maak embed` cannot be forgotten.** The eighteen scripts and the companion stylesheet live in `resources/` and are embedded into Scheme by a task. *The hard part* is that the check needs to compare two generated files while tolerating the reformatting the embedder itself performs.
- **Installation from an archive.** The three packaging recipes are documented as recipes to build. *The hard part* is a maintainer in each distribution willing to carry a fast-moving young package, which is a social problem the code cannot solve.
- **A density and direction audit.** `data-density`, `density-toggle`, `locale`, `bdi` and `bdo` exist, and the stylesheet is written in logical properties. *The hard part* is that density and RTL are properties of every component at once, so the check is either a browser pass over every shelf in every density and direction, or it is nothing.
- **Motion that respects the reader, everywhere.** The motion primitives (`fade-in`, `slide-in`, `collapse`, the `hg-motion-*` classes) exist, and `prefers-reduced-motion` is honoured where the stylesheet remembers to. *The hard part* is that the failure is invisible to whoever tests it — an author who has not asked for reduced motion cannot see the bug — so it needs an assertion, not a review.
- **A changelog a consumer can plan around.** `version.scm` and the README note that minor releases may rename a key argument. *The hard part* is not writing the file, it is the discipline of a deprecation window, which for a single-author project means deciding to carry old spellings for a release.
- **A per-component support statement.** Which browsers, which assistive technologies, which Guile versions a component is exercised against — written down rather than assumed. *The hard part* is that the only honest source is a browser matrix in CI, and that is the largest infrastructure change on this page.
- **A published, versioned stylesheet URL.** A consumer links `olive.min.css` from beside their page today, and the companion stylesheet is embedded in the library. Serving the companion sheet as its own cacheable, versioned file would let a page be upgraded without a redeploy. *The hard part* is that the embedded copy exists precisely so a consumer needs no asset pipeline, so this is a second delivery route rather than a replacement.

## New features that would be worth having

- **A server kit, not just a component kit.** The form-lifecycle module I keep circling: decode a submission, produce `(field . message)` pairs, render the page again with those pairs in the right slots, redirect on success. It is the piece of every server-rendered application that is easiest to get subtly wrong and least interesting to rewrite, and hygguile already has both ends of it (`validation-errors`, `validation-summary`) with nothing in between.
- **An `hg-doctor` for consumers.** Check that `olive.min.css` sits where the page expects it, that `(hygguile-recommended-resources)` is in the head, that a page's `lang` is set, that the font files declared by `custom-fonts` actually resolve, and that the version of the framework matches the version the stylesheet was written for. Every one of these is a known newcomer trap, and every one is mechanically checkable.
- **Email-safe rendering.** A parallel renderer that emits tables-in-tables with inline styles, from the same component calls, for the transaction mail every application ends up sending. *(Speculative — email clients are a different medium, and the temptation to make the components lie about their semantics is real.)*
- **Islands for the four components that genuinely need them.** The command palette filters, the table sorts, the carousel pages, the tray reorders — all currently enhanced by a script reading markup. A tiny, documented "island" convention would let those components own their script and their initial state instead of relying on a global file that looks for attributes. *(Speculative, and the main risk is that it re-opens the door to the hydration model this project exists to avoid.)*
- **A translation of the showcase, and then of the docs.** Listed in the README as a good first contribution. It is also the only honest way to find out whether the RTL and density work is real: a Dutch or Japanese showcase proves the logical properties and the type scale, where an English one merely does not contradict them.
- **A conformance page per component.** Not a demo — a page that states what a component guarantees and shows the failing case beside the passing one: the input with a helper and an error, the table with forty columns, the toolbar at 200% zoom. *(Speculative in form, but the showcase is already halfway there.)*
- **Server-side, no-server-required rendering for documents.** The same components rendered to a static HTML file or a PDF for a report or an invoice — the components are already functions from data to SXML, so the missing part is a page frame and a print stylesheet rather than a new idea. *(Speculative: print is a different medium, and the honest version of this may be "not this library".)*

The pattern in the speculative items is the same one as in the in-scope list: each moves a fact out of prose and into something a machine can check — an argument list, a token, an assertion, a contract. The two that do not fit that pattern (islands, email) are the two where the project's own philosophy is the obstacle rather than the guide, which is exactly why they are marked.

## Contributions that would move the needle

1. **Make one component declare its key arguments.** Not the framework — one component, well chosen, done completely: the macro or record, the docstring read from it, the spec asserting an unknown key raises. Why it is a good task: it is the smallest complete proof that statement 1 is achievable, and everything else retrofits from it.
2. **A real accessibility assertion.** Take one component family — `field.scm` is the obvious one — and add a browser-driven check for accessible names and error wiring. Why it is a good task: it upgrades the suite from "shape" to "meaning" for the surface where it matters most, and it proves the harness before anyone is asked to trust it.
3. **Close one of the `FIXME`s in `sxml.scm`.** *Why it is a good task:* two lines of comment mark the only place in the pipeline where a mistake becomes malformed HTML rather than an exception; the fix is small, the test is a property, and it is the kind of work that makes the next contributor trust the codebase.
4. **A component the catalogue is missing.** A `breadcrumb` variant, an `inline-edit`, whatever you needed and could not find — provided the markup stays native and the script, if any, is an enhancement. *Why it is a good task:* the component index is the project's contract and a gap in it is a real bug in somebody's application.
5. **A contrast pair or a keyboard case.** The gate and the specs both grow one assertion at a time, and each one is a bug that can never come back. *Why it is a good task:* an hour, no design decisions, and it compounds.
6. **One of the three packaging recipes, actually built.** Take `packaging/opensuse` and get it through an `osc build`, fixing whatever the recipe got wrong. *Why it is a good task:* it is the only route to statement 5 that does not require persuading a maintainer, and it would find the assumptions the recipes currently make about a Guile that is not the Guix one.
7. **Your application on the consumers list.** The README keeps a list of projects that use Hygguile because real usage is the best documentation. *Why it is a good task:* it costs nothing, and it is the only mechanism by which the gaps described here become visible from outside.

The ranking is value per hour. Items 1 to 3 are each a day or two and change the ratio of "the author knows" to "the suite knows"; item 6 is a weekend and changes who can install the thing. What is deliberately not on the list is a large new component family: the catalogue is already wider than most, and adding to it before the arguments are checkable makes the retrofit bigger without making it easier.

That last point is worth arguing, because it is the one place where a well-meaning contributor is most likely to be thanked and wrong. Hygguile's breadth is genuinely impressive — a hundred-odd components, a data grid with selection and resizing, a command palette — and breadth is not what is missing. What is missing is that the library does not yet *know* what it guarantees, and every new component added before that knowledge exists is one more thing to retrofit. If you want to add one, add it together with the assertion that would have caught it being wrong.

## Compared to related projects

| Project | What it is | Where hygguile differs |
|---|---|---|
| Hiccup | A Clojure library turning vectors into HTML | Hiccup is a syntax for HTML and stops there. Hygguile is the component library and design system above that syntax: the argument is about `aria-describedby` and error slots as much as about brackets. |
| Reagent, Helix, Helix-adjacent React wrappers | Client-side rendering with a virtual DOM and hydration | The opposite architecture. Hygguile has no client state, no hydration and no component that needs a runtime to be legible. |
| Guile's own `(sxml simple)` | The SXML-to-XML serialiser that ships with Guile | Hygguile ships its own, because Guile's emits `text/xml` conventions — a self-closing `<div />` that `text/html` reads as an unclosed tag — and because a serializer is the one place where the output contract can be enforced. |
| Haunt | A static site generator in Guile, with SXML templates | Haunt builds a site; hygguile builds the interface a site or an application shows. They compose: a Haunt site can use these components. |
| GNU Artanis | A Scheme web application framework with its own templating | Artanis is the server and the routing; hygguile is the view layer. LucidPlan is the working proof that they fit, and the missing piece — a documented form round trip — is what statement 4 is about. |
| htmx | Attribute-driven hypermedia enhancement of server-rendered HTML | The closest neighbour in philosophy: HTML from the server, enhanced where it helps. htmx brings its own request/swap semantics; hygguile brings components and leaves the requests to the server. |
| Bootstrap, Bulma, Pico, DaisyUI | CSS frameworks, some with a component vocabulary | They style markup you write. Hygguile emits the markup, keeps its native semantics, and is tested on it — and it builds on Olive CSS rather than being a CSS framework itself. |
| Shoelace, Lit, Web Components | Custom elements that need a runtime to render | A custom element that fails to upgrade is an empty box. Every hygguile component is HTML before any script runs, which is the whole reason the project exists. |
| Django forms and Jinja macros | A server-side form abstraction and a template layer | The nearest thing in *role*, and the most useful comparison: Django proved that a form abstraction belongs in a framework rather than in each application. Hygguile has the rendering half and not yet the lifecycle half. |
| Marko, Svelte's server output, Astro islands | Components compiled to server HTML, with interactivity added per island | The modern, well-funded version of the same instinct, and the one whose users hygguile would most plausibly interest if they wrote Scheme. They keep a build step and a component compiler; hygguile keeps a function that returns a list. |

What the others do that hygguile could still add: Django's form object — validation rules, bound data, per-field errors, all in one value the template reads — is the design hygguile is closest to reinventing badly. htmx's discipline about *when* a script is allowed to make a request is a better answer than "whatever the enhancement needs". And every CSS framework with a decade of use has a deprecation policy; hygguile's "pin a commit in production" is honest, and it is not that.

Where hygguile is ahead and should stay ahead: the markup it emits is the markup a screen reader and a crawler can use on the first byte, and the project treats that as a testable property rather than a slogan. Its contrast gate runs a browser over the real pages in every theme. Its components are named after the HTML they produce, which sounds like a detail and is in fact why the whole thing is learnable. And its size — no build step, no runtime, no client store — is a feature that the rest of the ecosystem is slowly rediscovering.

There is one comparison that cannot go in the table because it is not a competitor: the three projects already built on this — WikiMusic, LucidPlan and Byggsteg — are the most useful evidence the project has, and the least used. Every one of them re-implemented some part of the form round trip, because the library gave them `validation-errors` and stopped. That repetition is the argument for statement 4, and it is stronger than any comparison with a framework in another language.

## In the long run

The long bet is that server rendering is not a nostalgic choice but the correct default for the software most people actually write: forms, dashboards, admin panels, documentation, content. The industry spent a decade learning that a client-side application is expensive to build, expensive to run and expensive to keep correct, and the correction is already under way. Hygguile's position is that the correction should not stop at "render on the server and then hydrate" — it should reach the components, the state model, and the assumption that an interface needs a runtime at all.

The second bet is that accessibility is a property of the output rather than a checklist applied afterwards. Native elements, real labels, honest disclosure, contrast measured on rendered pixels: none of that is charity work bolted on at the end, it is what makes the components reusable in the first place. A framework that emits the right element cannot produce an inaccessible table by accident.

The third bet is about Scheme. Hygguile exists because its author wanted to build a web interface in Guile and found the pieces scattered; the deeper wager is that a Lisp is a better place to describe a document than a template language is, because a document is a tree and a Lisp is a tree notation. If that is true, the ecosystem question — how many people write Scheme — is a question about reach, not about correctness, and the answer is to make the library good enough that reach follows.

What would make these bets wrong is worth stating. If the ecosystem settles on "render on the server, then hydrate", then the distinction this project is built on becomes a matter of degree rather than of kind, and the advantage narrows to the size of the bundle — real, but not a thesis. If Guile's web ecosystem fragments further, a component library with no server kit stays a component library, and the missing form lifecycle will keep being rebuilt per consumer. And if accessibility tooling becomes good enough that any framework can be made accessible in an afternoon, then the largest part of this project's care becomes table stakes, and the argument has to move to the one thing that would remain: that the output is a document before it is an application.

## How to read this document

The items under "in scope and not built yet" are the ones the code has already committed to by cutting a seam; the rest are proposals, and the speculative ones are marked because they may well be wrong. Hygguile's README already tells you its minor releases may change a key argument — this document is not a promise to do any of the above faster, only an argument about which of them are worth the change.

Read the five statements as a filter on any change you are considering. Does it make a component call harder to get wrong, an escaping path provable, an accessibility claim measurable, a server round trip reusable, or an install possible? If it does none of those, it can still be a good contribution — the catalogue is proof that taste is a legitimate reason to add to this project — but it is not what this document is arguing for.

One caution about reading a document like this on a project that is one person's work: the honest scheduling is that statements 1 and 2 arrive slowly, because each requires retrofitting thirty modules, and that statement 4 may never arrive, because it is the one that needs somebody who is not the author. The direction is still worth writing down, if only so that a contribution arriving from outside can tell which of these it is pushing.

*This document describes intent, not commitments; the API reference, the showcase and the suite remain the only account of what hygguile does.*
